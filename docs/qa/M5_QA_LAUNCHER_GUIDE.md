# M5 disposable QA launcher (issue #21)

This is the current test-support procedure for the observed F15/F19 shell and evidence failures. It does not grant approvals or claim the September 12 acceptance gaps are closed. Use only synthetic data and an owned disposable fixture. The scripts live in `scripts/qa/`; they never edit `base/ui`, Riley's checkout, global WSL settings, Ollama, or Docker.

## Terminal roles and fresh setup

From **Windows PowerShell** in this isolated worktree, choose the WSL distro explicitly. The wrapper reads the actual Windows Git HEAD/dirty status (WSL Git cannot resolve this Windows-linked worktree pointer), converts the repository path, and calls the Bash entry. A clean committed source revision is required for `build`/`start`; `init` still records a dirty revision so it cannot silently become a reusable binary identity.

```powershell
git status --short
git rev-parse HEAD
.\scripts\qa\m5_launcher.ps1 -Distro Ubuntu init --name m5-acceptance
.\scripts\qa\m5_launcher.ps1 -Distro Ubuntu build
.\scripts\qa\m5_launcher.ps1 -Distro Ubuntu start
.\scripts\qa\m5_launcher.ps1 -Distro Ubuntu status
.\scripts\qa\m5_launcher.ps1 -Distro Ubuntu connection
```

The launcher uses `$HOME/.local/share/lumen-m5-qa/fixtures/<name>` **inside WSL's Linux filesystem**, not volatile `/tmp`. `selected.json` preserves the chosen fixture across terminals. The fixture manifest stores the workspace UUID, source SHA/dirty bit, model/port, config/database paths, binary hash and owned PID/start time; it contains no token. The bearer token is generated by Python's `secrets` module in a separate mode-0600 file. `connection` prints the URL, workspace ID, and token **file path**. Read that token locally when the browser connection dialog requires it; never put it in a URL, command argument, screenshot, issue, report, or committed file. If a browser still points at an old workspace, reconnect it using this fixture's displayed ID before interpreting an authorization failure.

In a new **WSL Bash** terminal, change to this worktree's WSL path (the PowerShell `wslpath` result) and resume the same selected fixture without copying UUIDs, shell exports, or the token:

```bash
cd /mnt/c/path/to/this/lumen-m5-windows-worktree
bash scripts/qa/m5_launcher.sh status
bash scripts/qa/m5_launcher.sh connection
```

The Bash entry refuses non-WSL Linux or Python older than 3.11. Use `select <name>` if more than one fixture exists. Initial `init` in this Windows-linked worktree should use PowerShell so Git metadata is supplied directly; subsequent Bash commands independently verify the Windows Git state through `git.exe`. The Bash core's `--source-sha` is for a normal Linux checkout or an operator-supplied verified value. An interrupted `init` can be retried under the same name; an owned incomplete staging directory is removed on retry and never becomes a selected partial fixture. Concurrent `init` calls are serialized. A foreign or symlinked stage is refused, not removed. No shell-local credentials are needed for later commands. The build uses `--locked`, two jobs and the stable Linux-side `$HOME/.cache/lumen-m5-cargo-target` from the [Cargo cache guide](M5_CARGO_CACHE_GUIDE.md), then reuses the hashed binary for the same clean fixture. It never runs `cargo clean` or shares Windows target artifacts.

## Observe, approve, and poll

`start` waits at most 30 seconds for the authenticated cheap readiness route and records the response. `status` prints the owned PID, readiness/HTTP error, port and evidence path without the bearer token. A bare sleep or `server_starting` log line is not a completed run. HTTP 401/403, wrong workspace, early exit and timeout remain failures. Model inference/GPU readiness is separate; see the [GPU policy guide](M5_GPU_POLICY_GUIDE.md).

For a known scheduled one-shot, record the exact job UUID, revision and **scheduled-for epoch milliseconds** returned by that test's authorized flow, then poll that occurrence only:

```bash
bash scripts/qa/m5_launcher.sh poll-job --job-id 'JOB-UUID' --revision 1 --scheduled-for-ms 1789256658516 --seconds 120
```

The example timestamp is historical, not a value to reuse. The helper reads the selected local SQLite fixture read-only and prints `scheduled`, `due`, `claimed`, `running`, `completed`, or a failure state with a finite deadline. `completed` requires both a succeeded occurrence and completed correlated run. Timeout is `inconclusive`, never success. The exact observed transitions are saved as machine-readable evidence.

Approvals are **never granted by this helper**. When a test creates a known run, inspect exactly that run and expected action kind before manually deciding in the normal UI/API:

```bash
bash scripts/qa/m5_launcher.sh approval-check --run-id 'RUN-UUID' --kind schedule.job.create
```

This returns a unique unexpired approval ID, expiry, fingerprint, scrubbed arguments and capabilities, or fails for an absent, ambiguous, changed-kind, expired, or HTTP-error response. Compare the full normalized action in the normal approval interface before deciding; the helper never grants it. Do not use an approval-list loop to grant arbitrary pending actions. Do not lengthen TTL to hide a slow test. A fresh request is needed if one expires.

## Evidence and destructive test lifecycle

Before any intentional DB tamper, take a named healthy snapshot. The command opens the **existing** database read-only and uses SQLite's [online backup API](https://www.sqlite.org/backup.html), which includes committed WAL state; it verifies the snapshot and stores its SHA-256. Copying only a live main `.sqlite3` file is not equivalent. Keep destructive tests on this disposable fixture; retain before/after state and verify expected refusal/no forbidden effect.

```bash
bash scripts/qa/m5_launcher.sh snapshot --label before-tamper
bash scripts/qa/m5_launcher.sh record --case G02 --outcome expected_refusal --command 'synthetic audit tamper test' --details '{"assertions":["audit verify refused corruption"]}'
bash scripts/qa/m5_launcher.sh attach --label G02-screen --file /path/to/sanitized-screenshot.png
bash scripts/qa/m5_launcher.sh stop
bash scripts/qa/m5_launcher.sh status
```

The evidence directory is a sibling of the fixture, keyed by fixture ID, so an interrupted shell or later cleanup does not erase it. Reports include source SHA, dirty bit, workspace, binary hash, timestamp, outcome, commands and details. The helper redacts its own token, bearer headers and secret-named JSON fields. `attach` also refuses raw fixture files and files containing obvious credential patterns, but it cannot identify arbitrary private user data inside a screenshot or free-text prompt. Inspect and sanitize source artifacts *before* `attach`/`record`; use synthetic inputs only. No raw DB, screenshot or evidence archive is committed by default. Retain the evidence directory and SHA-256 of any external archive in the final QA report.

Restore is destructive to **only this selected fixture** and requires its exact `fixture_id` from `status`. Stop the owned process first; neither command signals an unverified PID. `restore` refuses a missing/changed/symlinked snapshot or mismatched ownership and uses SQLite backup to repopulate the selected database. It does not recalculate a tampered audit chain.

```bash
bash scripts/qa/m5_launcher.sh restore --label before-tamper --confirm 'THIS-FIXTURE-ID'
bash scripts/qa/m5_launcher.sh start
bash scripts/qa/m5_launcher.sh status
```

Only when finished, stop and explicitly delete the selected fixture root. `cleanup` refuses an unowned or symlinked tree, requires exact fixture-ID confirmation, and **retains evidence and the Cargo cache**:

```bash
bash scripts/qa/m5_launcher.sh stop
bash scripts/qa/m5_launcher.sh cleanup --confirm 'THIS-FIXTURE-ID'
```

If a recorded PID exists but no longer matches its Linux start time, executable and config command, the helper refuses to signal or mutate the fixture. If the shell was interrupted just after launching the server, a later command can adopt only a process with this fixture's recorded launch ID, token, binary and config; it then applies the same PID/start-time checks. Investigate any other PID/port manually; the helper never terminates unrelated services or runs `wsl --shutdown`. A failed start can be resumed with `status`/`start` after inspecting `server.log`. A missing fixture, invalid name/ID, occupied unrelated port, changed config, token or binary hash, bad SQLite source, or missing tools is a visible error rather than implicit recreation.

This launcher does not itself execute the full M5 acceptance matrix, operate a browser, inject model prompts, decide approvals, run the negative tamper mutation, or prove GPU use. Each such case still needs an actual observed result or `NOT RUN`/`BLOCKED` in the final acceptance report. The Python checks are `python3 -m unittest discover -s scripts/qa -p test_m5_launcher.py -v`; set `LUMEN_M5_QA_TEST_BINARY` to a built WSL `lumen` binary to include its owned live-server test.
